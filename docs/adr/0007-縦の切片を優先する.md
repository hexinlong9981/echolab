# ADR-0007: 機能を横に広げる前に、最小の端から端までを先に通す

- 状態: 採用
- 日付: 2026-10-03

## 背景

EchoLab は計算サービス・Agent 編成・ゲートウェイ・数値トレース検証器・評価・画像読み取り・Web UI など、
複数の要素で構成されます。中心となる仕組みは数値トレース検証器で、その有効性は端から端までを通して初めて測れます。
要素をどの順序で実装するかを決める必要がありました。

## 決定

1. **M2 は縦の切片にする。** 「質問 → ゲートウェイ → calc-engine → 数値トレース検証器 → 出典付きの回答」を CLI で通す。
   数値の忠実度の評価と、コストの上限（日次・月次）も M2 に入れる。
2. **住宅ローンのパックを M3 で追加する。** 小さいコストで「コアを変えずにドメインを足せる」ことを示す（ADR-0003）。
3. **ディレクトリは実装するときに作る。** 計画は `docs/architecture.md` のロードマップに書く。

## 理由

- 端から端までを先に通すことで、検証器の有効性を早い段階で評価によって測れる。以降の機能追加も、その指標を見ながら進められる。
- コストの上限を最初の切片に含めることで、LLM を使う部分を最初から安全に運用できる。
- 2 つ目のドメインを早く足すことで、コアのドメイン非依存性を CI で継続的に検査できる。
- リポジトリの構成が実装と一致し、ロードマップは `docs/architecture.md` に一元化される。

## 却下した案

| 案 | 却下した理由 |
|---|---|
| 要素ごとに横に作り込み、最後に統合する | 検証器の有効性を測れるのが後になり、設計の判断材料が遅れる |

## 影響

- `README.md`・`README.en.md`・`docs/architecture.md` のロードマップは、この順序（M1〜M5）に従う。
- M2 から評価（数値の忠実度）を測り、M4 で評価パイプラインを CI に組み込む。
