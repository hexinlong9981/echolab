Traces and Evals

For every question, EchoLab records the process, event by event, in an “execution trace” file. It also ships with a “faithfulness eval” that uses a fixed set of test cases to check whether answers contain numbers of unknown origin. This page shows you how to find and read traces, and how to run the evals yourself and understand the eval report.

Where traces are stored

ItemDetails
Location.echolab/traces/ under the repository root (listed in .gitignore, never committed). You can change it with --trace-dir DIR
File name<run ID>.jsonl, one file per question. A run ID looks like 20261003T031424Z-28df54: the UTC time plus 6 random hex digits, so sorting by file name gives chronological order
Which file is mine?The last line of the CLI output, トレース: … (“Trace”), is the path of this run's file, and the second-to-last line shows the 実行 ID (run ID)
FormatJSON Lines: one event per line. Every line has ts (UTC time with milliseconds), run_id and event (event type). Each event is written to disk immediately, so even if the program fails partway through, what already happened is preserved
Eval tracesWhen you run the evals, each case's trace goes into traces/ under the eval raw-records directory (default evals/reports/raw/traces/)

Hands-on: ask a question, then inspect the trace

Below we first ask a question in scripted mode (no API key needed), then list the trace directory, and finally use EchoLab's own read_trace function to print the events in order. All output is from an actual run (the answer is abbreviated).

The status line reads: status answered, rejected 1 time, cost $0.0000, run ID. To see only one kind of event, pass a second argument to read_trace; for example, to see only the verifier's verdicts:

.venv/bin/python -c "
from core.trace import read_trace
for v in read_trace('.echolab/traces/20261003T031424Z-28df54.jsonl', 'verdict'):
    print(v['draft'], v['ok'], v['problems'])
"
# Actual output:
1 False ['数値「936」の出典がありません。ツールの結果は [[出典ID]] で引用し、差や比は比較ツールで計算してください（質問にある数値の引用は可）。']
2 True []

Draft 1 failed with the message “The number 936 has no source. Cite tool results as [[source ID]] and compute differences and ratios with the compare tools; quoting numbers from the question is allowed.” Draft 2 passed. (Asking a question in scripted mode creates a new trace file in .echolab/traces/ and changes nothing else in the repository.)

How to read a trace

Event types

eventWhen it is writtenFields worth looking at
questionAt the start, oncequestion the original question, domain the domain pack, llm (ScriptedLLM for scripted mode, AnthropicLLM for the real Claude), model, tools the tools available for this run
llm_callAfter each Claude callstop_reason (tool_use = wants to call tools, end_turn = submitted a draft), usage token counts, usd cost, text the draft, tool_uses
tool_callBefore each tool callname (e.g. damage_expected), input
tool_resultAfter each tool calloutcome.call_id (c1…), outcome.sources (source IDs and values, unverified_inputs unverified data), outcome.error (explanation when the gateway rejected the call or the input was invalid)
verdictAfter each draft is checkeddraft draft number, ok passed or not, problems reasons for rejection, cited cited source IDs, template the original draft
answerAt the end, oncestatus, answer the final text, cited, cost_usd, drafts / drafts_rejected, llm_calls / tool_calls
budget_exceededWhen a cost cap is reached and the run stops without calling Claudereason
llm_errorWhen calling Claude fails (for example, no API key is set)kind the failure category (credentials no credentials, auth authentication failed, transient rate limit / overload / network, other anything else), error the raw SDK message

Tips for reading traces
  • Start with the last line, answer: the status, cost and number of rejections are all there at a glance.
  • Suspicious number in the answer? Find its source ID in answer.cited (e.g. c4.change), then find the source_id with the same name in tool_result to see the original value and the tool that calculated it.
  • Was a draft rejected? Look at problems in verdict to see which number had no source.
  • Values are stored as strings (e.g. "6192.000000"), so they are never rounded.

Faithfulness eval: test cases that check for numbers of unknown origin

The eval feeds the cases in evals/faithfulness/cases.yaml to EchoLab one by one and checks the results. There are currently 8 cases:

Case IDWhat it checksExpected result
damage-basicCiting expected damage and each part of its breakdownanswered, no rejections
echo-scoreCiting an Echo score (value and percentage)answered
gacha-unverifiedValues from unverified data automatically get the noteanswered, with note
compare-buildsParallel calculations + compare tools (difference, rate of increase)answered, cites c1–c4
tool-error-recoveryUnderstanding a tool's input error and calling againanswered, cites c2
bad-draft-raw-numberA draft that writes a number directly is rejected and rewritten with a citationanswered, 1 rejection
bad-draft-derived-and-unknown-idA self-calculated difference and a nonexistent source ID are both rejectedanswered, 2 rejections
never-correctedWhen repeated rejections never fix the draft, a fixed reply with no numbers is returned insteadfallback, 3 rejections

Running the evals (scripted mode)

Scripted mode needs neither an API key nor Java (it uses the test calculation service) and finishes in a few seconds. Below, the report and raw records are written to a temporary directory (for example /tmp/ug3/) so that no files in the repository are changed:

(The report title is “Eval report: numeric faithfulness”, followed by the date, the LLM and the case file (8 cases), then the metrics and a per-case results table in which 合格 means “passed”. The last line says: “In scripted mode, usage (token counts) is made-up values written in the script; the cost is only for checking the calculation.” The report in the terminal is a Markdown table; the “content” column is omitted here to save space. The exit code is 0 when every case passes and faithfulness is 1.0, and 1 otherwise.)

Run a single case

--case never-corrected (you can repeat --case for several). Measured: fallback, 3 drafts (下書き), 3 rejections (差し戻し), passed (合格). If an ID is misspelled, no case runs; the available IDs are listed and the exit code is 2.

Where the report goes

--out PATH writes the Markdown report (without it, the report is only printed). The raw records faithfulness-<llm>-<time>.jsonl and each case's trace are written to --raw-dir, default evals/reports/raw/ (not committed).

Use a different set of cases

--cases FILE.yaml, in the same format as evals/faithfulness/cases.yaml.

What the metrics in the report mean

Metric (as in the report)MeaningValue this run
忠実度
(faithfulness)		The share of answers returned to the user that contain not a single unsourced number. Answers that passed the verifier are checked again; for fixed replies, it confirms they contain no numbers at all. By EchoLab's design, this value must be 1.0001.000
差し戻し率
(rejection rate)		The share of all drafts that the verifier rejected. It measures how often the AI makes mistakes, not how often answers are wrong: rejected drafts never reach the user. The scripted-mode cases contain deliberate mistakes, so this value is high here0.462 (6 / 13)
合格したケース
(cases passed)		Whether the status, citations, number of rejections, notes and so on match the expectations8 / 8
費用の合計
(total cost, USD)		Total Claude cost across all cases. In scripted mode the token counts are made-up numbers written in the script, used only to check the cost calculation itself0.028120

In the per-case table, “下書き” is the number of drafts, “差し戻し” the number of rejections, “引用した出典” the source IDs cited by the final answer, and “合否” whether the case passed (with the reason when it did not). The baseline report committed to the repository, evals/reports/scripted-baseline.md, matches the result above exactly.

Scripted mode vs. the real Claude

Scripted mode --llm scripted (default)Real Claude --llm anthropic
AI answersFollow the script written in each case; identical every timeOnly the question is given to the real Claude (claude-opus-5-5); may differ each time
Calculation serviceTest calculation service (Python reference implementation); no Java neededThe real Java calculation service (needs Java 21 and a built jar)
RequirementsNothingCredentials such as ANTHROPIC_API_KEY; incurs costs
Cost accountingUses a temporary ledger; does not affect the real cost capsRecorded in the real ledger .echolab/costs.jsonl and subject to the daily / monthly caps (default 1 / 10 USD)
What is checkedEverything: status, faithfulness, notes, cited source IDs, number of rejections, whether the script was fully usedStatus, faithfulness and notes (citations and rejection counts vary with the AI, so they are not checked)
Where to runLocally and in CIOnly manually, locally; only the aggregated report is committed. CI has no API key
What happens without an API keyMeasured: when you ask a question without --llm scripted, EchoLab does not crash. It returns a fixed reply explaining the cause and the fix, “Claude API の認証情報が見つからないため、回答できませんでした。環境変数 ANTHROPIC_API_KEY を設定する（または ant auth login でログインする）か、…” (“Could not answer because no Claude API credentials were found. Set the environment variable ANTHROPIC_API_KEY (or log in with ant auth login), or …”), with status llm_error and exit code 1. The trace contains an llm_error event with "kind": "credentials" and “Claude API の認証情報が見つかりません（ANTHROPIC_API_KEY などを設定してください）” (“Claude API credentials not found (set ANTHROPIC_API_KEY or similar)”). The same applies to evals with --llm anthropic: without a key, cases end with llm_error and no cost is incurred.

The command for an eval with the real Claude (with a key, and with the Java calculation service built):

JAVA_HOME=$HOME/.local/jdk/21 .venv/bin/python -m core.evals --llm anthropic --out evals/reports/<name>.md

Cases run one at a time, in order (not in parallel, so costs cannot run away). The LLM line of the report includes the model name.
