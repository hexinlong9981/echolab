Troubleshooting and FAQ

Every problem on this page has been reproduced in a real environment. First check whether the output under “Symptom” matches what you see, then follow “Cause” and “Fix”.

First, figure out which kind of problem it is

Figure 1: Troubleshooting decision path. First check whether there is a status line (状態), then check its value

When setup or startup fails, there is no status line: the CLI prints one line エラー: … (“Error: …”) to standard error explaining the cause and how to fix it, exits with code 2, and does not print a traceback (add --debug if you need one). When there is a status line, the answer on screen states the category of the cause, and more detail is in the execution trace. A general way to look:

# The run ID (実行 ID) is in the status line; substitute it here
grep -E 'llm_error|budget_exceeded|verdict|tool_result' .echolab/traces/<実行 ID>.jsonl

① java not found

The message says: “Error: the executable java for service calc-engine was not found. Install JDK 21 and put java on PATH, or set the environment variable JAVA_HOME (so that $JAVA_HOME/bin/java exists).” The second line means “add --debug to show the traceback”.

Cause: without --fake-backend, the CLI has to start the Java calculation service, but there is no java on PATH and JAVA_HOME is not set (the CLI checks this before starting the subprocess). On WSL, a Java installed on the Windows side usually cannot be used directly from the Linux side.

Fix (any one of these):

  • Set JAVA_HOME to JDK 21: export JAVA_HOME=$HOME/.local/jdk/21 (adjust to where you actually installed it). The CLI then uses $JAVA_HOME/bin/java automatically.
  • Or add JDK 21's bin to PATH.
  • To skip Java for now: add --fake-backend.

② jar not found (calculation service not built)

The message says: “Error: the jar for service calc-engine does not exist: …/calc-engine-mcp.jar. Build the jar first: (cd services/calc-engine && ./gradlew bootJar)”.

Cause: Java was found, but services/calc-engine/build/libs/calc-engine-mcp.jar does not exist. The launch command in config/services.yaml is java -jar <path>, and the CLI checks that the file after -jar exists before starting Java, so it never starts a process that would exit immediately. If the jar exists but the service exits right after starting, you see エラー: サービス calc-engine を起動できませんでした（…）。起動コマンド: … (“Error: could not start service calc-engine (…). Launch command: …”), also with exit code 2.

Fix: build the jar, then go back to the repository root and try again.

cd services/calc-engine && JAVA_HOME=$HOME/.local/jdk/21 ./gradlew bootJar -q
ls build/libs/        # you should see calc-engine-mcp.jar
cd ../..

③ llm_error: no credentials (or invalid credentials)

The answer says: “Could not answer because no Claude API credentials were found. Set the environment variable ANTHROPIC_API_KEY (or log in with ant auth login), or use scripted mode (--llm scripted), which needs no API key.” The sources table is empty (“no sources cited”).

Cause: the default --llm anthropic needs Anthropic credentials. The CLI sorts failures into 4 kinds based on the Anthropic SDK's exception type, and the answer on screen states the kind and what to do. The trace's llm_error event has the category kind and the SDK's raw message:

④ budget_exceeded: cost cap reached

Setting the daily cap to 0 lets you reproduce this safely in scripted mode (scripted mode only uses a one-off temporary ledger and does not affect your real ledger):

The answer says: “Today's (UTC) cost has reached the daily cap, so I cannot answer right now (used 0 USD / cap 0 USD). It becomes available again when the UTC date changes. The cap can be changed with the environment variable ECHOLAB_DAILY_USD or caps_usd.daily in config/budget.yaml.”

Cause: before every AI call, the totals for today (UTC) and this month (UTC) in the ledger are compared with the caps; once a cap is reached, no more calls are made. Scripted mode checks this too (see the example above). The answer itself states whether it is the daily (今日 / 日次) or monthly (今月 / 月次) cap, the amount used / the cap, when it will reset, and which environment variable or config/budget.yaml key changes it.

Fix:

  • Wait for the UTC day to change (00:00 UTC, for example 08:00 in Beijing or 09:00 in Tokyo) or for the next month (UTC).
  • If you really need to, raise it temporarily: export ECHOLAB_DAILY_USD=2.00 (use ECHOLAB_MONTHLY_USD for the monthly cap).
  • Check that you are not using a different ledger by mistake: does ECHOLAB_LEDGER point to an unexpected file? If a line in the ledger cannot be parsed, the program does not skip it; it stops with exit code 2 and reports the file and line number (see ⑦).

⑤ Tool input errors (usually corrected automatically)

If the AI calls a tool with wrong parameters (a missing field, a value out of range, both or neither of rules and banner, and so on), the calculation service does not stop. Instead, it returns the error message to the AI as the result so the AI can fix it and call again. In the run below, the first call omitted rules, and the second call added them and succeeded:

(my-toolerr.yaml is a script for reproducing this, taken from the eval case tool-error-recovery. The question asks for the probability of getting the featured character with one pull from pity count 8 with a guaranteed featured pull, and spells out the rules: base rate 0.1, soft pity from 5 rising by 0.1 per pull, hard pity 10, featured rate 0.5, guaranteed after losing the 50/50. The answer says “The probability of getting it with the next pull is 60%.” The error in the trace says “specify exactly one of rules and banner”.)

When the parameters do not match the tool's input specification (JSON Schema), the gateway returns the error to the AI before the tool is even called. The message is in Japanese and includes the field path, for example 入力が不正です: pulls: 20000 は最大値 10000 より大きい値です (“invalid input: pulls: 20000 is greater than the maximum 10000”) or 入力が不正です: (全体): 必須の項目がありません: pulls (“invalid input: (root): required field missing: pulls”).

How to tell: the source ID is c2.probability, not c1…; the 1st call (c1) failed. What you need to do: usually nothing. If, with the real Claude, tool errors keep happening and you never get an answer, spell out all the conditions the calculation needs in your question (for example the gacha rules' base rate, soft pity and hard pity, or say explicitly that the sample banner should be used).

⑥ fallback: verification did not pass

(my-fallback.yaml is a script for reproducing this, taken from the eval case never-corrected. The answer says: “Sorry. I could not produce an answer whose calculation results can be traced to their sources, so I will not give an answer containing numbers. Please make the conditions more specific and ask again.”)

Cause: all three of the AI's drafts wrote numbers directly (“the probability is about 73.4%”, “the probability is 0.734”, “the probability is about 73% ([[c1.probability|%1]])”) instead of citing tool results with placeholders. Each time, the verifier gave feedback like this (problems in the trace's verdict event):

数値「73.4%」の出典がありません。ツールの結果は [[出典ID]] で引用し、差や比は比較ツールで計算してください（質問にある数値の引用は可）。

(“The number 73.4% has no source. Cite tool results as [[source ID]] and compute differences and ratios with the compare tools; quoting numbers from the question is allowed.”) After 3 rejections, EchoLab would rather give no numbers than give numbers that might be wrong. Fix: as the message suggests, make the conditions more specific and ask again; numbers you wrote in the question can be quoted in the answer as is.

FAQ

Why doesn't it answer questions outside the tools' scope (such as character tier lists)?

EchoLab's design principle is that numbers only come from tools. The current tools are: expected damage (damage.expected), Echo score (echo.score), gacha probability (gacha.probability_within, gacha.simulate) and comparison (compare.diff, compare.ratio). A number that no tool can calculate cannot appear in an answer; if it does, the verifier rejects the draft and the run ends with fallback. The gateway also only allows calls to tools declared in domain.yaml. See What you can ask.

Why is the sample data marked “未確認” (unverified)?

The values in domains/wuwa/data are sample values compiled by hand. They have not been checked against official game data and are marked verified: false. They can still be used in calculations, but whenever a calculation uses them, the answer always ends with ※ この回答の数値の一部は、未確認のサンプルデータに基づいています。 (“Some numbers in this answer are based on unverified sample data.”), and the “未確認データ” (unverified data) column of the sources table names the exact data entry (such as gacha_rules:featured-character). To get results that do not depend on sample data, give all parameters in your question.

How much does one use cost?

Scripted mode (--llm scripted) and the default eval mode cost nothing; the status line shows 費用: $0.0000 (“cost”). Real Claude mode is billed per token: in config/budget.yaml, claude-opus-5-5 costs 4.00 USD per million input tokens and 20.00 USD per million output tokens (cache read 0.20, cache write 5.00). The actual cost of each run is shown in the status line and recorded call by call in .echolab/costs.jsonl; by default spending is capped at 1 USD per day and 10 USD per month. See Cost caps & data trust.

Where is my question sent?

Only in --llm anthropic mode (the default) are the question, system prompt, tool definitions and tool results sent to Anthropic's API. Scripted mode runs entirely on your machine, and the calculation service also runs locally as a subprocess. In addition, the question and the full process of every run are stored in plain text locally in .echolab/traces/ (git-ignored); you can delete them yourself when you no longer need them.

In scripted mode I changed the question. Why is the answer the same?

In scripted mode, the tool calls and drafts are determined by the script file; the question is used only for recording and verification (numbers written in the question may be quoted in the answer). In testing, changing the question to “こんにちは” (“hello”) still produced the same comparison result with the same script. To have the system actually understand your question, use real Claude mode.

Is there a graphical interface (web version)?

No. Currently it can only be used from the command line. A web UI, trace replay and an eval dashboard are part of roadmap milestone M5 and are not implemented yet. See Roadmap.

Can I use it without installing a JDK?

Yes. Add --fake-backend to use the Python reference implementation instead of the Java calculation service (it has been checked against the same golden cases as the Java implementation). The only difference is that the fake service does not provide the Monte Carlo simulation tool gacha_simulate. Raw values in the sources table are returned with 6 decimal places, the same as with the Java version.
