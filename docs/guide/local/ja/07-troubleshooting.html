① Python のバージョン(version)が古(ふる)い

原(げん)因(いん)：このプロジェクト(project)は Python 3.12 を基(き)準(じゅん)にしており（CI は 3.12 を使(つか)い、ruff の対(たい)象(しょう)バージョン(version)も py312 です）、コード(code)は 3.11 以(い)降(こう)にしかない機(き)能(のう)を使(つか)っています。実(じっ)際(さい)に試(ため)すと、3.10 の仮(か)想(そう)環(かん)境(きょう)でも pip install は成(せい)功(こう)しますが、実(じっ)行(こう)したとたんに上(うえ)のエラー(error)になります。（3.11 でも単(たん)体(たい)テスト(test)は通(とお)りましたが、プロジェクト(project)が対(たい)応(おう)するバージョン(version)ではありません。）

対(たい)処(しょ)：Python 3.12 以(い)降(こう)を入(い)れ、古(ふる)い仮(か)想(そう)環(かん)境(きょう)を削(さく)除(じょ)してから作(つく)り直(なお)してください。仮(か)想(そう)環(かん)境(きょう)は、作(つく)ったときの Python に固(こ)定(てい)されるためです。

python3.12 --version
rm -rf .venv
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt

② 仮(か)想(そう)環(かん)境(きょう)を有(ゆう)効(こう)にしていない

原(げん)因(いん)：pytest、ruff と依(い)存(ぞん)ライブラリ(library)は、.venv の中(なか)にしか入(はい)っていません。多(おお)くの Linux ディストリビューション(distribution)には python というコマンド(command)がなく（python3 だけです）、システム(system)の python3 には依(い)存(ぞん)パッケージ(package)が入(はい)っていません。新(あたら)しいターミナル(terminal)を開(ひら)くたびに、有(ゆう)効(こう)にし直(なお)す必(ひつ)要(よう)があります。

対(たい)処(しょ)：

cd ~/echolab
source .venv/bin/activate      # プロンプトの前に (.venv) が出れば成功
which python pytest            # どちらも ~/echolab/.venv/bin/ を指しているはず

有(ゆう)効(こう)にしたくない場(ば)合(あい)は、フルパス(full path)で書(か)くこともできます：.venv/bin/python -m core.agent …、.venv/bin/pytest。No module named 'core' が出(で)る場(ば)合(あい)は、現(げん)在(ざい)のディレクトリ(directory)がリポジトリ(repository)のルート(root)ではありません。

③ pip でインストール(install)できない（ネットワーク(network)、オフライン(offline)）

（説(せつ)明(めい)のみで、再(さい)現(げん)はしていません。）pip install -r requirements-dev.txt は、PyPI から anthropic、mcp、pyyaml、jsonschema、pytest、ruff などのパッケージ(package)をダウンロード(download)します。よくある状(じょう)況(きょう)は次(つぎ)のとおりです。

プロキシ(proxy)が必(ひつ)要(よう)なネットワーク(network)長(なが)いあいだ再(さい)試(し)行(こう)したあと Could not find a version that satisfies the requirement … になるHTTPS_PROXY を設(せっ)定(てい)するか、pip install --proxy http://… を使(つか)う。社(しゃ)内(ない)ネットワーク(network)では、そのルート(route)証(しょう)明(めい)書(しょ)を信(しん)頼(らい)させる必(ひつ)要(よう)がある場(ば)合(あい)もある
ミラー(mirror)を使(つか)う公(こう)式(しき)のインデックス(index)がとても遅(おそ)い、またはつながらないpip install -i <ミラーの URL> -r requirements-dev.txt を使(つか)うか、PIP_INDEX_URL を設(せっ)定(てい)する

Java の側(がわ)も同(どう)様(よう)です。初(しょ)回(かい)の ./gradlew は services.gradle.org と Maven のリポジトリ(repository)からダウンロード(download)するため、オフライン(offline)の環(かん)境(きょう)では ~/.gradle のキャッシュ(cache)を前(まえ)もって用(よう)意(い)しておく必(ひつ)要(よう)があります。

④ java が見(み)つからない

（my-banner.yaml は 4 ページ(page)目(め) で書(か)いたデモ(demo)用(よう)の台(だい)本(ほん)です。--fake-backend を付(つ)けないコマンド(command)なら、どれでも同(おな)じ結(けっ)果(か)になります。）

原(げん)因(いん)：PATH に java がなく、JAVA_HOME も設(せっ)定(てい)されていません。CLI は子(こ)プロセス(process)を起(き)動(どう)する前(まえ)にこれを確(たし)かめています。~/.bashrc の設(せっ)定(てい)は、新(あたら)しく開(ひら)いた対(たい)話(わ)型(がた)のターミナル(terminal)でしか効(き)きません。

対(たい)処(しょ)：4 ページ(page)目(め) の手(て)順(じゅん)で JDK 21 を入(い)れ、export JAVA_HOME=$HOME/.local/jdk/21（実(じっ)際(さい)の場(ば)所(しょ)に合(あ)わせてください）を実(じっ)行(こう)します。当(とう)面(めん) Java を使(つか)わない場(ば)合(あい)は、--fake-backend を付(つ)けてください。

⑤ PATH にあるのが古(ふる)いバージョン(version)の java

CLI が JAVA_HOME を使(つか)うのは、PATH に java が見(み)つからないときだけです。PATH にすでに Java 8 や 17 があると、JAVA_HOME が JDK 21 を指(さ)していても、古(ふる)いバージョン(version)で jar を起(き)動(どう)してしまいます。次(つぎ)は、Java 8 を指(さ)す java を使(つか)って再(さい)現(げん)したものです。

読(よ)み方(かた)：最(さい)初(しょ)の数(すう)行(ぎょう)は、Java の子(こ)プロセス(process)が標(ひょう)準(じゅん)エラー(error)に書(か)いたメッセージ(message)です。class file version 61.0 にはもっと新(あたら)しい Java が必(ひつ)要(よう)で、up to 52.0 はいまの Java が Java 8 であることを示(しめ)します。最(さい)後(ご)の行(ぎょう)が CLI のエラー(error)です。

対(たい)処(しょ)：JDK 21 を PATH の先(せん)頭(とう)に置(お)き、確(たし)かめます。

export PATH="$JAVA_HOME/bin:$PATH"
java -version          # 1 行目が openjdk version "21…" になっているはず
which java             # JDK 21 の bin/java を指しているはず

⑥ JAVA_HOME が間(ま)違(ちが)ったディレクトリ(directory)を指(さ)している

JAVA_HOME は JDK のルートディレクトリ(root directory)（その下(した)に bin/java があるところ）でなければなりません。bin ディレクトリ(directory)や、複(ふく)数(すう)の JDK を置(お)いている 1 つ上(うえ)のディレクトリ(directory)ではありません。間(ま)違(ちが)っていると、CLI のエラー(error)は ④ とまったく同(おな)じになります（JAVA_HOME=~/.local/jdk、つまり 1 つ上(うえ)のディレクトリ(directory)で実(じっ)測(そく)）。Gradle Wrapper のエラー(error)のほうが直(ちょく)接(せつ)的(てき)です。

対(たい)処(しょ)：JAVA_HOME を bin/java を含(ふく)むディレクトリ(directory)に設(せっ)定(てい)し、ls $JAVA_HOME/bin/java で確(たし)かめます。JAVA_HOME を Windows 側(がわ)の JDK に向(む)けないでください（⑧ を参(さん)照(しょう)）。

⑦ jar がない

原(げん)因(いん)：Java は見(み)つかりましたが、jar をまだビルド(build)していません（クローン(clone)したばかり、./gradlew clean を実(じっ)行(こう)した、build/ を削(さく)除(じょ)した、など）。対(たい)処(しょ)：エラー(error)に示(しめ)されたコマンド(command)でビルド(build)します。サブシェル(subshell)で実(じっ)行(こう)するので、終(お)わるとリポジトリ(repository)のルート(root)に戻(もど)ったままです：(cd services/calc-engine && ./gradlew bootJar)。同(おな)じ状(じょう)況(きょう)では、エンドツーエンドテスト(end-to-end test)はスキップ(skip)されます。テスト(test)と評(ひょう)価(か)を実(じっ)行(こう)する をご覧(らん)ください。

⑧ WSL で Windows 側(がわ)のツール(tool)を混(ま)ぜてしまった

WSL は既(き)定(てい)で、Windows の PATH（/mnt/c/…）を Linux の PATH の後(うし)ろに付(つ)け足(た)します。そのため、java.exe や python.exe のような .exe 付(つ)きの Windows のプログラム(program)も呼(よ)べてしまいますが、Linux 側(がわ)の java や python3 の代(か)わりにはなりません。

  • Java：CLI と Gradle が探(さが)すのは java で、java.exe ではありません。Windows 側(がわ)に JDK が入(はい)っていても役(やく)に立(た)ちません（上(うえ)の例(れい)はそもそも Java 8 です）。WSL の中(なか)に Linux 版(ばん)の JDK 21 を別(べつ)に入(い)れてください（4 ページ(page)目(め)）。
  • Python：同(おな)じく、WSL の中(なか)で Linux の python3.12 を使(つか)って仮(か)想(そう)環(かん)境(きょう)を作(つく)ってください。WSL の中(なか)のリポジトリ(repository)を Windows の Python で動(うご)かさないでください。
  • リポジトリ(repository)の場(ば)所(しょ)：リポジトリ(repository)は Linux のファイルシステム(file system)（例(れい)：~/echolab）にクローン(clone)し、/mnt/c/… には置(お)かないでください。ファイルシステム(file system)をまたぐアクセス(access)はとても遅(おそ)く、Gradle のビルド(build)も pytest も目(め)に見(み)えて遅(おそ)くなります。ファイル(file)の権(けん)限(げん)がおかしくなることもあります。
  • 改(かい)行(ぎょう)コード(code)：WSL の中(なか)で git clone すれば問(もん)題(だい)ありません。リポジトリ(repository)の .gitattributes で、gradlew は LF を使(つか)うよう決(き)められています。Windows のツール(tool)でコピー(copy)したり書(か)き換(か)えたりして CRLF になってしまうと、次(つぎ)のエラー(error)になります。

対(たい)処(しょ)：WSL のホームディレクトリ(home directory)で git clone し直(なお)すか、sed -i 's/\r$//' gradlew で復(ふっ)帰(き)文(も)字(じ)を取(と)り除(のぞ)きます。

⑨ Docker：permission denied

これが起(お)きるのは、4 ページ(page)目(め) の任(にん)意(い)の Docker によるビルド(build)を使(つか)うときだけです。

原(げん)因(いん)：Docker デーモン(daemon)のソケット(socket)には root と docker グループ(group)しかアクセス(access)できず、現(げん)在(ざい)のユーザー(user)は docker グループ(group)に入(はい)っていません。

対(たい)処(しょ)（説(せつ)明(めい)のみで、このページ(page)では実(じっ)行(こう)していません）：

sudo usermod -aG docker "$USER"   # docker グループに追加する
# そのあとログアウトしてログインし直す（WSL では Windows 側で wsl --shutdown を実行してから開き直す）か、
# いまのターミナルでだけ一時的に有効にする：
newgrp docker
docker ps                          # エラーが出なければ成功
  • docker グループ(group)に入(い)れることは、そのユーザー(user)に root と同(どう)等(とう)の権(けん)限(げん)を与(あた)えることに等(ひと)しいので、自(じ)分(ぶん)の開(かい)発(はつ)用(よう)のマシン(machine)でだけ行(い)ってください。
  • Docker Desktop の WSL 統(とう)合(ごう)を使(つか)う場(ば)合(あい)は、Docker Desktop の設(せっ)定(てい)でお使(つか)いのディストリビューション(distribution)の統(とう)合(ごう)を有(ゆう)効(こう)にしてください。その場(ば)合(あい)のメッセージ(message)は上(うえ)とは異(こと)なります。
  • Docker に手(て)間(ま)をかけたくない場(ば)合(あい)は、手(て)元(もと)のマシン(machine)に JDK 21 を入(い)れてビルド(build)すれば、同(おな)じ結(けっ)果(か)が得(え)られます。

それでも解(かい)決(けつ)しないときは

  • CLI の設(せっ)定(てい)や起(き)動(どう)のエラー(error)は、--debug を付(つ)けるとトレースバック(traceback)をすべて表(ひょう)示(じ)します。
  • プログラム(program)がすでに状(じょう)態(たい)の行(ぎょう)（状態: …）を表(ひょう)示(じ)している場(ば)合(あい)、問(もん)題(だい)は回(かい)答(とう)の層(そう)にあります。認(にん)証(しょう)情(じょう)報(ほう)、コスト(cost)の上(じょう)限(げん)、検(けん)証(しょう)の不(ふ)合(ごう)格(かく)、ツール(tool)の入(にゅう)力(りょく)の誤(あやま)りなどについては トラブルシューティング(troubleshooting)と FAQ をご覧(らん)ください。
  • 引(ひき)数(すう)、環(かん)境(きょう)変(へん)数(すう)、終(しゅう)了(りょう)コード(code)の詳(くわ)しい説(せつ)明(めい)は コマンドリファレンス(command reference) にあります。
  • 環(かん)境(きょう)の準(じゅん)備(び)に戻(もど)る：必(ひつ)要(よう)なもの・セットアップ(setup)。
