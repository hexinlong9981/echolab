Troubleshooting local runs

This page covers only problems with setting up the environment: Python, the virtual environment, the JDK, the jar, WSL and Docker. If the program runs but the answer is not what you expected (llm_error, budget_exceeded, fallback and so on), see Troubleshooting and FAQ in the user guide.

About the output on this pageEvery problem that could be reproduced was reproduced on a fresh clone of the repository, and the "symptom" outputs are real. The repository path has been shortened to ~/echolab, paths in the home directory to ~ or /home/user, the user name has been replaced with user, and long outputs are cut with "…". Problems that cannot be reproduced safely (such as offline installation) are only described, and are marked as such.

① Python is too old

Cause: the project targets Python 3.12 (CI uses 3.12, and ruff's target version is py312), and the code uses features that only exist from 3.11 on. In our test, pip install succeeded in a 3.10 virtual environment, but running the program failed with the error above. (3.11 also passed the unit tests in our test, but it is not a supported version.)

Fix: install Python 3.12 or newer, then delete the old virtual environment and create it again; a virtual environment is tied to the Python that created it:

python3.12 --version
rm -rf .venv
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt

② The virtual environment is not activated

Cause: pytest, ruff and the dependencies are installed only in .venv. Many Linux distributions have no python command (only python3), and the system python3 does not have the dependencies installed. You need to activate the environment again in every new terminal.

Fix:

cd ~/echolab
source .venv/bin/activate      # success when (.venv) appears before the prompt
which python pytest            # both should point into ~/echolab/.venv/bin/

If you prefer not to activate it, write the full path instead: .venv/bin/python -m core.agent …, .venv/bin/pytest. If you see No module named 'core', the current directory is not the repository root.

③ pip cannot install (network, offline)

(Described only, not reproduced.) pip install -r requirements-dev.txt needs to download packages such as anthropic, mcp, pyyaml, jsonschema, pytest and ruff from PyPI. Common situations:

SituationTypical signWhat to do
A network that needs a proxyCould not find a version that satisfies the requirement … after a long series of retriesSet HTTPS_PROXY, or use pip install --proxy http://…; a corporate network may also require trusting its root certificate
Using a mirrorThe official index is slow or unreachablepip install -i <mirror URL> -r requirements-dev.txt, or set PIP_INDEX_URL
A fully offline machineCannot connectOn a machine with network access and the same OS and Python version, run pip download -r requirements-dev.txt -d wheels, copy wheels/ over, then run pip install --no-index --find-links wheels -r requirements-dev.txt
Creating the virtual environment failsensurepip is not available on Debian/UbuntuInstall the matching system package, such as sudo apt install python3.12-venv

The same applies on the Java side: the first ./gradlew run downloads from services.gradle.org and Maven repositories, so an offline environment needs a prepared ~/.gradle cache.

④ java not found

(my-banner.yaml is the demo script written on page 4; any command without --fake-backend gives the same result.) The error means: "Error: executable java for service calc-engine not found. Install JDK 21 and put java on PATH, or set the JAVA_HOME environment variable so that $JAVA_HOME/bin/java exists." The next line says that --debug shows the traceback.

Cause: there is no java on PATH and JAVA_HOME is not set. The CLI checks this before starting the subprocess. Settings in ~/.bashrc only take effect in newly opened interactive terminals.

Fix: install JDK 21 as described on page 4, then run export JAVA_HOME=$HOME/.local/jdk/21 (adjust to the actual location). If you do not need Java for now, add --fake-backend.

⑤ An old java on PATH

The CLI uses JAVA_HOME only when java is not found on PATH. If Java 8 or 17 is already on PATH, the jar is started with that old version even when JAVA_HOME points to JDK 21. Reproduced below with a java that points to Java 8:

How to read it: the first lines are what the Java subprocess wrote to standard error; class file version 61.0 needs a newer Java, and up to 52.0 means the running Java is Java 8. The last line is the CLI's error: "Error: could not start service calc-engine (…). Start command: java -jar …".

Fix: put JDK 21 at the front of PATH, then check:

export PATH="$JAVA_HOME/bin:$PATH"
java -version          # the first line should be openjdk version "21…"
which java             # should point to bin/java of JDK 21

⑥ JAVA_HOME points to the wrong directory

JAVA_HOME must be the JDK's root directory (the one containing bin/java), not the bin directory and not a parent directory holding several JDKs. When it is wrong, the CLI's error is exactly the same as in ④ (tested with JAVA_HOME=~/.local/jdk, one level too high). The Gradle Wrapper's error is more direct:

Fix: set JAVA_HOME to the directory that contains bin/java, and confirm with ls $JAVA_HOME/bin/java. Do not point JAVA_HOME at a JDK on the Windows side (see ⑧).

⑦ The jar does not exist

The error means: "Error: the jar for service calc-engine does not exist: …. Build the jar first: (cd services/calc-engine && ./gradlew bootJar)".

Cause: Java was found, but the jar has not been built yet (a fresh clone, after ./gradlew clean, or after deleting build/). Fix: build it with the command given in the error, which returns you to the repository root afterwards: (cd services/calc-engine && ./gradlew bootJar). In the same situation the end-to-end tests are skipped; see Run tests & evals.

⑧ Mixing in Windows tools under WSL

By default, WSL appends the Windows PATH (/mnt/c/…) to the Linux PATH. So Windows programs with .exe, such as java.exe and python.exe, can be called, but they cannot replace the Linux java or python3:

  • Java: the CLI and Gradle look for java, not java.exe. A JDK installed on the Windows side does not help (and in the example above it is Java 8 anyway). Install the Linux JDK 21 inside WSL (page 4).
  • Python: likewise, create the virtual environment in WSL with the Linux python3.12; do not run the repository in WSL with the Windows Python.
  • Repository location: clone the repository into the Linux file system (such as ~/echolab), not under /mnt/c/…. Access across file systems is slow, so Gradle builds and pytest become noticeably slower, and file permissions may also be wrong.
  • Line endings: just use git clone inside WSL; the repository's .gitattributes requires LF for gradlew. If a file was copied or rewritten with CRLF by a Windows tool, you get the error below:

Fix: git clone again into your WSL home directory, or remove the carriage returns with sed -i 's/\r$//' gradlew.

⑨ Docker: permission denied

You only run into this when using the optional Docker build described on page 4.

Cause: the Docker daemon's socket is accessible only to root and the docker group, and the current user is not in the docker group.

Fix (described only, not run for this page):

sudo usermod -aG docker "$USER"   # add yourself to the docker group
# then sign out and back in (in WSL, run wsl --shutdown on the Windows side and reopen),
# or apply it to the current terminal only:
newgrp docker
docker ps                          # no error means it worked
  • Membership in the docker group effectively gives that user root-level privileges, so do this only on your own development machine.
  • If you use Docker Desktop's WSL integration, enable integration for your distribution in Docker Desktop's settings; the message in that case differs from the one above.
  • If you would rather not deal with Docker, install JDK 21 locally and build there; the result is the same.
