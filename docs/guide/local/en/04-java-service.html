RunJDK 21calc-engine

Run with the Java calc service

Drop --fake-backend and the CLI starts the real calc service, calc-engine (an MCP server built with Java 21 and Spring Boot). This page covers, in order: installing JDK 21, building the jar, how the CLI starts the service, running the example, and the "data references" that only the Java service supports.

About the output on this pageEvery command and output on this page comes from a real run on a fresh clone of the repository (Linux/WSL2, Python 3.12, Temurin 21). For readability, the long path of the repository has been shortened to ~/echolab, the user name has been replaced with user, and the middle of long outputs is replaced with "…". Timings depend on your machine and network and are only a rough guide.

Two calculation backends for scripted mode

In Run in scripted mode (no API key) we added --fake-backend: the calculations are done by the Python reference implementation (tests/core/fakes.py), and no Java is needed. Without it, the CLI starts the Java calc service as configured in config/services.yaml. Both give the same numbers for the same question; the differences are:

--fake-backend (Python reference implementation)Without it (Java calc service)
RequiresOnly the Python environmentJDK 21 + a built jar
Time for the bundled example (measured)About 3.2 secondsAbout 8.5 seconds (the extra time is mostly JVM and Spring startup)
Data references (banner/profile)Not supported; the tool returns an errorSupported, with an "unverified" (未確認) note added automatically
Used forDemos, unit tests, evals in scripted modeReal use, end-to-end tests (pytest -m e2e)

1. Install JDK 21

Any JDK 21 distribution works. The example below installs Eclipse Temurin from an archive into your home directory, without root (x64 Linux/WSL2; for other platforms, pick the matching package on the Adoptium website; on macOS you can also install temurin@21 with Homebrew).

mkdir -p ~/.local/jdk
curl -L -o /tmp/temurin21.tar.gz \
  https://api.adoptium.net/v3/binary/latest/21/ga/linux/x64/jdk/hotspot/normal/eclipse
tar -xzf /tmp/temurin21.tar.gz -C ~/.local/jdk        # extracts a directory such as jdk-21.0.12.1+1 (the version changes)
ln -sfn ~/.local/jdk/jdk-21.0.12.1+1 ~/.local/jdk/21  # a fixed path without the version number makes upgrades easier
echo 'export JAVA_HOME=$HOME/.local/jdk/21' >> ~/.bashrc
export JAVA_HOME=$HOME/.local/jdk/21

The download is about 198 MB. Once the line is in ~/.bashrc, new terminals set JAVA_HOME automatically.

java does not need to be on PATHBefore starting the service, the CLI looks for java: if it is on PATH, that one is used; if it is not on PATH but JAVA_HOME is set, $JAVA_HOME/bin/java is used instead (see resolve_executable in core/gateway/mcp_backend.py). The Gradle Wrapper also reads JAVA_HOME. So setting JAVA_HOME is enough.
Mind the orderThe CLI uses JAVA_HOME only when java is not found on PATH. If an older java (such as Java 8 or 17) is already on PATH, the CLI uses it and the service fails to start. In that case, put JDK 21 at the front of PATH: export PATH="$JAVA_HOME/bin:$PATH". For the actual error, see Troubleshooting local runs.

2. Build the jar

From the repository root, go to services/calc-engine and build the executable jar with the bundled Gradle Wrapper. The first run downloads Gradle itself (8.14.3) and all dependencies, so it needs the network and took about 2 minutes in our run; later builds take a few seconds.

  • The result is services/calc-engine/build/libs/calc-engine-mcp.jar (about 24 MB, including Spring Boot and all dependencies). This is the path that config/services.yaml refers to.
  • Gradle itself and the dependencies are cached in ~/.gradle/ (change the location with GRADLE_USER_HOME), not in the repository. build/ is ignored by Git.
  • Compilation runs Error Prone with -Xlint:all -Werror: any compiler warning fails the build.
  • After changing Java code, run ./gradlew bootJar again; the CLI does not rebuild automatically. The data under domains/wuwa/data is read at run time, so changing data does not require a rebuild.

3. How the CLI starts the calc service

How to start it is configured in config/services.yaml; all paths are relative to the repository root:

schema_version: 1
services:
  calc-engine:
    transport: stdio
    command: ["java", "-jar", "services/calc-engine/build/libs/calc-engine-mcp.jar"]
    env:
      ECHOLAB_DATA_ROOT: domains

Each time you run python -m core.agent (without --fake-backend), the gateway starts the jar as a subprocess and talks to it with the MCP protocol over standard input/output; the process exits when the question is done. It does not listen on any network port.

sequenceDiagram
  participant U as You (terminal)
  participant C as CLI and gateway<br/>Python
  participant J as calc-engine<br/>java -jar subprocess
  U->>C: python -m core.agent "question" --llm scripted …
  C->>C: Read config/services.yaml
  C->>C: Check that java and the jar exist<br/>if not, exit with code 2
  C->>J: Start subprocess (working directory: repository root)
  C->>J: MCP initialize (stdin/stdout)
  J-->>C: Initialized
  C->>J: tools/list
  J-->>C: damage_expected, echo_score, gacha_…
  loop Whenever the LLM requests a tool call
    C->>J: tools/call (waits up to 30 seconds each)
    J-->>C: Result JSON (numbers, unverified data IDs)
  end
  C->>J: Close session, process exits
  C-->>U: Answer, source table, status line
Figure 1: What passes between the CLI and the Java calc service during one question (MCP over stdio)
  • Check first, then start: if java is found neither on PATH nor via JAVA_HOME, or the jar does not exist, the CLI does not start the process; it prints a one-line エラー: … ("Error: …", including how to fix it) and exits with code 2.
  • Standard output is for MCP only: the service prints no startup banner and writes logs only to standard error, so nothing leaks into the answer.
  • Environment variables: the values under env are defaults; if your shell already sets a variable with the same name, the shell's value wins.

For how the agent, the gateway and the verifier fit together, see What happens behind the scenes.

The answer and the source table are exactly the same as with --fake-backend (both backends return numbers to 6 decimal places); for a translation of the Japanese output, see page 3. On the same machine, the run took about 3.2 seconds with --fake-backend and about 8.5 seconds with the Java service. Every question starts the JVM and Spring Boot afresh, which accounts for the extra time; the calculations themselves take a few milliseconds. The user time is larger than real because the JVM uses several threads in parallel during startup.

Scripted mode + Java serviceThe run above is still in scripted mode (--llm scripted): the LLM's replies come from the script, but every number is really calculated by the Java service. If a calculation result differed from what the script expects, the later steps would no longer line up. This combination is exactly what the end-to-end tests use; see Run tests & evals.

5. Data references (Java service only)

Some tools can, instead of taking their parameters directly, refer by ID to the sample data bundled with the repository (domains/wuwa/data/v2.x/). Use one form or the other, not both:

Tool (MCP name)Given directlyData referenceExample ID
gacha_probability_within, gacha_simulaterulesbannerfeatured-character
echo_scoreweightsprofilesample-crit-attacker

The repository has only one example script, so here we write a small two-turn script, my-banner.yaml (in the repository root, not committed): turn 1 calls the gacha probability tool with banner, and turn 2 cites the result with a placeholder. The draft is in Japanese: "The chance of getting the limited character within 80 pulls is [[c1.probability|%1]]."

# Demo script for a banner data reference: a banner ID instead of rules given directly
turns:
  - tool_uses:
      - name: gacha_probability_within
        input: {banner: featured-character, start_pity: 0, guaranteed: false, pulls: 80}
  - text: 80 回以内に限定キャラクターを獲得できる確率は [[c1.probability|%1]] です。

The question asks "What is the chance of getting the limited character within 80 pulls?", and the answer says it is 60.6%.

  • The sample data is marked verified: false (not checked against official game data). The Java service returns the IDs of the unverified data it used (gacha_rules:featured-character) together with the result, and a note is added automatically at the end of the answer: 「※ この回答の数値の一部は、未確認のサンプルデータに基づいています。」 ("Some of the numbers in this answer are based on unverified sample data."). The LLM cannot leave this note out.
  • The 「未確認データ」 (unverified data) column of the source table shows exactly which data was used. For what the note means, see Reading the answers.

The same script fails with --fake-backend: the Python reference implementation only accepts rules given directly, so the tool returns an error and the script's turns no longer line up.

The error means: "the run did not follow the script (check the combination of question, script and --fake-backend): called after the script's responses (2) were used up"; the next line says that --debug shows the traceback. The tool error recorded in the trace is 「入力が不正です: 'rules'」 ("invalid input: 'rules'").

The tools' input descriptions (JSON Schema) list banner and profile, so real Claude may also choose to refer to the sample data; to get such questions answered, use the Java service.

6. The data directory: ECHOLAB_DATA_ROOT

The Java service reads domain.yaml from $ECHOLAB_DATA_ROOT/wuwa/, then finds the data files through its data_dir. The default is domains from config/services.yaml, relative to the repository root (the subprocess's working directory). To use different data (such as a version you have checked yourself), set the environment variable of the same name in your shell to override it:

ECHOLAB_DATA_ROOT=$PWD/domains python -m core.agent "…" --llm scripted --script my-banner.yaml   # same as the default
ECHOLAB_DATA_ROOT=/path/to/my-data python -m core.agent "…"                                       # the directory must contain wuwa/domain.yaml

If the directory is wrong, the service does not stop; it returns the error as the tool result (real Claude sees this error and can adjust). In our run with ECHOLAB_DATA_ROOT=/tmp/echolab-nodata (a directory that does not exist), the script above ended with エラー: 台本どおりに進みませんでした… ("Error: the run did not follow the script…") because its later turns no longer lined up, and the tool error recorded in the trace was ("data file not found"):

"error": "gacha_probability_within: データファイルがありません: /tmp/echolab-nodata/wuwa/domain.yaml"

This directory is read only for data references (banner/profile, or echo_score without max_roll); calculations with every parameter given directly are not affected.

Alternative: build with Docker (optional)

If you would rather not install a JDK on your machine, you can build and test inside the official Gradle image (which includes JDK 21). The command below is taken from the README; run it in services/calc-engine:

cd services/calc-engine
docker run --rm -u "$(id -u):$(id -g)" -e GRADLE_USER_HOME=/cache \
  -v "$HOME/.gradle-echolab:/cache" -v "$(cd ../.. && pwd):/w" -w /w/services/calc-engine \
  gradle:8-jdk21 ./gradlew check
PartWhat it does
--rmRemoves the container when it finishes
-u "$(id -u):$(id -g)"Runs as your own user, so the generated build/ is not owned by root
-e GRADLE_USER_HOME=/cache and -v "$HOME/.gradle-echolab:/cache"Keeps Gradle's download cache in ~/.gradle-echolab on the host, so later runs do not download again
-v "$(cd ../.. && pwd):/w" and -w /w/services/calc-engineMounts the whole repository (the tests read the golden cases and data in domains/wuwa) and runs in the calc-engine directory
gradle:8-jdk21 ./gradlew checkRuns the tests and static checks; replace check with bootJar to only build the jar
NoteDocker only handles the build. At run time the CLI still runs java -jar … on your machine, so to answer questions with the Java service you still need JDK 21 locally (the jar built in Docker can be used as is). This Docker command was not run in the environment used for this page; if you see permission denied … docker.sock, see Troubleshooting local runs.
