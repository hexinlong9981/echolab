本页只处理环境搭建阶段的问题：Python、虚拟环境、JDK、jar、WSL、Docker。程序已经运行、但回答不符合预期（llm_error、budget_exceeded、fallback 等）的问题，见使用说明中的 故障排除与 FAQ。

关于本页的输出能复现的问题都在一份全新克隆的仓库上实际复现过，「症状」里是真实输出。仓库路径缩写为 ~/echolab，主目录下的路径缩写为 ~ 或 /home/user，用户名替换为 user，长输出用「…」省略。无法安全复现的问题（如离线安装）只作说明，并已注明。

① Python 版本过旧

原因：项目以 Python 3.12 为准（CI 使用 3.12，ruff 的目标版本也是 py312），代码用到了 3.11 起才有的功能。实测 3.10 的虚拟环境里 pip install 可以成功，但一运行就出现上面的错误。（3.11 实测也能通过单元测试，但不是项目支持的版本。）

解决：安装 Python 3.12 或更新的版本，删除旧的虚拟环境后重建——虚拟环境会固定创建它时所用的 Python：

python3.12 --version
rm -rf .venv
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt

② 虚拟环境没有激活

原因：pytest、ruff 和依赖库都只装在 .venv 里。很多 Linux 发行版没有 python 这个命令（只有 python3），而系统的 python3 没有安装依赖。每开一个新终端，都需要重新激活。

解决：

cd ~/echolab
source .venv/bin/activate      # 提示符前出现 (.venv) 即成功
which python pytest            # 都应指向 ~/echolab/.venv/bin/

不想激活时，也可以直接写完整路径：.venv/bin/python -m core.agent …、.venv/bin/pytest。如果出现 No module named 'core'，说明当前目录不是仓库根目录。

③ pip 无法安装（网络、离线）

（说明，未复现。）pip install -r requirements-dev.txt 需要从 PyPI 下载 anthropic、mcp、pyyaml、jsonschema、pytest、ruff 等包。常见情况：

情况典型表现处理
需要代理的网络长时间重试后报 Could not find a version that satisfies the requirement …设置 HTTPS_PROXY，或用 pip install --proxy http://…；公司网络可能需要信任其根证书
使用镜像源官方源很慢或不可达pip install -i <镜像地址> -r requirements-dev.txt，或设置 PIP_INDEX_URL
完全离线的机器无法连接在能联网、且操作系统与 Python 版本相同的机器上执行 pip download -r requirements-dev.txt -d wheels，把 wheels/ 拷过去后执行 pip install --no-index --find-links wheels -r requirements-dev.txt
创建虚拟环境就失败Debian／Ubuntu 上提示 ensurepip is not available安装对应的系统包，如 sudo apt install python3.12-venv

Java 一侧同理：第一次运行 ./gradlew 要从 services.gradle.org 和 Maven 仓库下载，离线环境需要事先准备好 ~/.gradle 缓存。

④ 找不到 java

（my-banner.yaml 是 第 4 页 中编写的演示台本，用任何不加 --fake-backend 的命令都会得到同样的结果。）错误的意思是：找不到服务 calc-engine 的可执行文件 java；请安装 JDK 21 并把 java 加入 PATH，或设置 JAVA_HOME（使 $JAVA_HOME/bin/java 存在）。

原因：PATH 上没有 java，也没有设置 JAVA_HOME。CLI 在启动子进程之前就做了检查。~/.bashrc 里的设置只对新开的交互式终端生效。

解决：按 第 4 页 安装 JDK 21，然后 export JAVA_HOME=$HOME/.local/jdk/21（按实际位置）。暂时不用 Java 时，加 --fake-backend。

⑤ PATH 上是旧版本的 java

CLI 只在 PATH 上找不到 java 时才使用 JAVA_HOME。如果 PATH 上已经有 Java 8 或 17，即使 JAVA_HOME 指向 JDK 21，也会用旧版本启动 jar。下面用一个指向 Java 8 的 java 复现：

怎么看：前几行是 Java 子进程写到标准错误的信息，class file version 61.0 以上需要更新的 Java，up to 52.0 表示当前是 Java 8；最后一行是 CLI 的报错「无法启动服务 calc-engine」。

解决：让 JDK 21 排在 PATH 最前面，然后确认：

export PATH="$JAVA_HOME/bin:$PATH"
java -version          # 第一行应为 openjdk version "21…"
which java             # 应指向 JDK 21 的 bin/java

⑥ JAVA_HOME 指错了目录

JAVA_HOME 必须是 JDK 的根目录（其下有 bin/java），不是 bin 目录，也不是存放多个 JDK 的上级目录。指错时，CLI 的报错与 ④ 完全相同（实测 JAVA_HOME=~/.local/jdk，即上一级目录）。Gradle Wrapper 的报错更直接：

解决：把 JAVA_HOME 设为包含 bin/java 的那个目录，并用 ls $JAVA_HOME/bin/java 确认。不要把 JAVA_HOME 指向 Windows 侧的 JDK（见 ⑧）。

⑦ jar 不存在

原因：找到了 Java，但还没有构建 jar（新克隆的仓库、执行过 ./gradlew clean、或删掉了 build/）。解决：按报错里给出的命令构建，然后回到仓库根目录：(cd services/calc-engine && ./gradlew bootJar)。端到端测试在同样的情况下会被跳过，见 运行测试与评估。

⑧ 在 WSL 中混用了 Windows 侧的工具

WSL 默认把 Windows 的 PATH（/mnt/c/…）追加到 Linux 的 PATH 后面。因此 java.exe、python.exe 这样带 .exe 的 Windows 程序也能被调用，但它们不能代替 Linux 侧的 java 或 python3：

  • Java：CLI 和 Gradle 找的是 java，不是 java.exe。Windows 侧装了 JDK 也没有用（上例还是 Java 8）。请在 WSL 里另装 Linux 版 JDK 21（第 4 页）。
  • Python：同理，在 WSL 里用 Linux 的 python3.12 创建虚拟环境；不要用 Windows 的 Python 去运行 WSL 中的仓库。
  • 仓库位置：把仓库克隆到 Linux 文件系统（如 ~/echolab），不要放在 /mnt/c/…。跨文件系统访问很慢，Gradle 构建和 pytest 都会明显变慢，文件权限也可能不对。
  • 换行符：在 WSL 里用 git clone 即可；仓库的 .gitattributes 规定 gradlew 使用 LF。如果文件经由 Windows 工具复制或改写成了 CRLF，就会出现下面的错误：

解决：在 WSL 的主目录里重新 git clone；或者执行 sed -i 's/\r$//' gradlew 去掉回车符。

⑨ Docker：permission denied

只在使用 第 4 页 的可选 Docker 构建方式时才会遇到。

原因：Docker 守护进程的套接字只允许 root 和 docker 组访问，而当前用户不在 docker 组里。

解决（说明，本页未执行）：

sudo usermod -aG docker "$USER"   # 加入 docker 组
# 然后注销并重新登录（WSL 中可在 Windows 侧执行 wsl --shutdown 后重开），
# 或只在当前终端临时生效：
newgrp docker
docker ps                          # 不再报错即可
  • 加入 docker 组相当于给予该用户 root 级别的权限，请只在自己的开发机上这样做。
  • 使用 Docker Desktop 的 WSL 集成时，请在 Docker Desktop 的设置里为当前发行版开启集成；它的提示与上面不同。
  • 不想处理 Docker 时，直接在本机安装 JDK 21 构建即可，结果相同。
