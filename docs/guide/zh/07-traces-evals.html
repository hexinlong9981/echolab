进阶执行轨迹忠实度评估

执行轨迹与评估

每次提问，EchoLab 都会把过程一条一条记进一个“执行轨迹”文件；另外还附带一套“忠实度评估”，用固定的考题检查“答案里有没有来历不明的数字”。本页教你找到并读懂轨迹，以及自己运行评估、看懂评估报告。

轨迹保存在哪里

项目内容
位置仓库根目录下的 .echolab/traces/（已在 .gitignore 中，不会被提交）。可以用 --trace-dir 目录 改到别处
文件名<运行 ID>.jsonl，每次提问一个文件。运行 ID 形如 20261003T031424Z-28df54：UTC 时间 + 6 位随机十六进制，按文件名排序就是时间顺序
怎么知道是哪个CLI 输出的最后一行 トレース: …（“轨迹”）就是这次的文件路径，倒数第二行有 実行 ID（运行 ID）
格式JSON Lines：一行一个事件。每行都有 ts（UTC 时间，毫秒）、run_id、event（事件类型）。每写一条就立刻落盘，程序中途出错也能留下已发生的部分
评估的轨迹运行评估时，每道考题的轨迹放在评估原始记录目录下的 traces/ 里（默认 evals/reports/raw/traces/）

动手：提问后查看轨迹

下面先运行一次台本模式的提问（不需要 API 密钥），再列出轨迹目录，最后用 EchoLab 自带的 read_trace 函数把事件按顺序打印出来。输出都是实际运行的结果（答案部分略）。

只想看某一类事件时，给 read_trace 第二个参数，例如只看验证器的判定：

.venv/bin/python -c "
from core.trace import read_trace
for v in read_trace('.echolab/traces/20261003T031424Z-28df54.jsonl', 'verdict'):
    print(v['draft'], v['ok'], v['problems'])
"
# 实际输出：
1 False ['数値「936」の出典がありません。ツールの結果は [[出典ID]] で引用し、差や比は比較ツールで計算してください（質問にある数値の引用は可）。']
2 True []

（运行台本模式的提问会在 .echolab/traces/ 新建一个轨迹文件，此外不改动仓库。）

怎么读一份轨迹

事件类型

event什么时候写值得看的字段
question开始时，1 条question 问题原文、domain 领域包、llm（ScriptedLLM 为台本，AnthropicLLM 为真实 Claude）、model、tools 本次可用工具
llm_call每次调用 Claude 后stop_reason（tool_use＝要调用工具，end_turn＝交了草稿）、usage token 数、usd 费用、text 草稿、tool_uses
tool_call每个工具调用前name（如 damage_expected）、input
tool_result每个工具调用后outcome.call_id（c1…）、outcome.sources（出典 ID 与数值、unverified_inputs 未确认数据）、outcome.error（网关拒绝或输入错误时的说明）
verdict每份草稿检查后draft 第几份、ok 是否通过、problems 退回理由、cited 引用的出典 ID、template 草稿原文
answer结束时，1 条status、answer 最终文字、cited、cost_usd、drafts / drafts_rejected、llm_calls / tool_calls
budget_exceeded达到成本上限、没有调用 Claude 就停止时reason
llm_error调用 Claude 失败时（例如没有设置 API 密钥）kind 失败的分类（credentials 没有凭据、auth 认证失败、transient 限流・过载・网络、other 其他）、error SDK 的原始信息

读轨迹的小技巧
  • 先看最后一行 answer：状态、费用、退回了几次一目了然。
  • 答案里的某个数字可疑？在 answer.cited 里找到出典 ID（如 c4.change），再在 tool_result 里找同名的 source_id，就能看到原始值和计算它的工具。
  • 被退回过？看 verdict 里的 problems，就知道哪个数字没有出典。
  • 数值以字符串保存（如 "6192.000000"），不会被四舍五入。

内容询问带明细的期望伤害；剧本 LLM 调用一次 damage_expected，用占位符引用总值和 5 个乘区。
用意确认回答中的所有数字都来自工具结果（ADR-0001、ADR-0008），连明细也能给出出处。
结果通过（符合预期）。 状态为 answered。 共 1 稿，退回 0 次。 引用出处 6 个。
评价一次通过，说明每个乘区的值都能追溯到出处 ID。公式是否与游戏实际一致不在检查范围内。这是用剧本 LLM 跑的，证明的是机制有效，并不保证真实 Claude 也会这样表现。
echo-score　引用声骸评分（值与百分比）
内容给出声骸词条、权重和最大值并请求评分；LLM 调用 echo_score，引用分数和占理想值的百分比。

报告里的指标是什么意思

指标（报告原文）含义这次的值
忠実度
（忠实度）		返回给用户的答案中，一个无出典数字都没有的比例。通过验证的答案会被再检查一遍；固定回答则确认里面没有任何数字。按 EchoLab 的设计，这个值必须是 1.0001.000
差し戻し率
（退回率）		所有草稿中被验证器退回的比例。它衡量的是 AI 犯错的频率，不是答案出错的比例——被退回的草稿不会给到用户。台本模式的考题故意包含错误，所以这里偏高0.462（6 / 13）
合格したケース
（通过的考题）		状态、引用、退回次数、注记等是否与期望一致8 / 8
費用の合計
（总费用，美元）		所有考题的 Claude 费用合计。台本模式的 token 数是台本里写的假数字，只用来检查费用计算本身0.028120

每题一行的表格中，“下書き”是草稿数，“差し戻し”是退回次数，“引用した出典”是最终答案引用的出典 ID，“合否”是否通过（不通过时写出原因）。仓库里提交的基准报告 evals/reports/scripted-baseline.md 与上面的结果完全一致。

台本模式 vs 真实 Claude

台本模式 --llm scripted（默认）真实 Claude --llm anthropic
AI 的回答按考题里写好的台本，每次都一样只把问题交给真实 Claude（claude-opus-5-5），每次可能不同
计算服务测试用计算服务（Python 参考实现），不需要 Java真实的 Java 计算服务（需要 Java 21 和构建好的 jar）
需要什么什么都不需要ANTHROPIC_API_KEY 等认证信息；会产生费用
费用记账用临时账本，不影响真实的成本上限记入真实账本 .echolab/costs.jsonl，受每日 / 每月上限约束（默认 1 / 10 美元）
检查哪些项目全部：状态、忠实度、注记、引用的出典 ID、退回次数、台本是否用完状态、忠实度、注记（引用和退回次数因 AI 而异，不检查）
在哪里跑本地和 CI 都可以只在本地手动运行，只提交汇总后的报告。CI 没有 API 密钥
没有 API 密钥时会怎样实测：不带 --llm scripted 运行提问时，EchoLab 不会崩溃，而是返回说明原因和对策的固定回答 “Claude API の認証情報が見つからないため、回答できませんでした。環境変数 ANTHROPIC_API_KEY を設定する（または ant auth login でログインする）か、…”，状态为 llm_error，退出码 1，轨迹里有一条 llm_error 事件："kind": "credentials"、“Claude API の認証情報が見つかりません（ANTHROPIC_API_KEY などを設定してください）”。用 --llm anthropic 评估时也一样：没有密钥的考题以 llm_error 结束，不会产生费用。

用真实 Claude 评估时的命令（有密钥、Java 计算服务已构建时）：

JAVA_HOME=$HOME/.local/jdk/21 .venv/bin/python -m core.evals --llm anthropic --out evals/reports/<名字>.md

考题按顺序一题一题执行（不并行，避免费用失控）。报告的 LLM 一行会写上模型名。
