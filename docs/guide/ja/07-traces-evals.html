応用実行トレース忠実度の評価

実行トレースと評価

EchoLab は質問のたびに、処理の流れを 1 件ずつ「実行トレース」ファイルに記録します。また、決まった試験問題で「回答に出所の分からない数値が含まれていないか」を確かめる「数値の忠実度の評価」も備えています。このページでは、トレースの見つけ方と読み方、そして評価を自分で実行してレポートを読む方法を説明します。

トレースの保存場所

項目内容
場所リポジトリのルートにある .echolab/traces/（.gitignore 済みで、コミットされません）。--trace-dir ディレクトリ で別の場所に変えられます
ファイル名<実行 ID>.jsonl。質問 1 回につき 1 ファイルです。実行 ID は 20261003T031424Z-28df54 のような形（UTC の時刻 + 6 桁のランダムな 16 進数）で、ファイル名順に並べるとそのまま時刻順になります
どのファイルか分かる方法CLI の出力の最終行 トレース: … が今回のファイルのパスです。その 1 つ上の行に 実行 ID があります
形式JSON Lines：1 行に 1 イベント。どの行にも ts（UTC の時刻、ミリ秒まで）、run_id、event（イベントの種類）があります。1 件書くたびにすぐディスクへ書き出すので、途中でエラーが起きても、それまでの記録は残ります
評価のトレース評価を実行すると、各問題のトレースは評価の生データのディレクトリ内の traces/ に置かれます（既定は evals/reports/raw/traces/）

やってみよう：質問してからトレースを見る

まず台本モードで質問を 1 回実行し（API キーは不要）、次にトレースのディレクトリを一覧表示し、最後に EchoLab に付属の read_trace 関数でイベントを順に表示します。出力はすべて実際の実行結果です（回答の部分は省略）。

特定の種類のイベントだけを見たいときは、read_trace に 2 つ目の引数を渡します。たとえば検証器の判定だけを見るには：

.venv/bin/python -c "
from core.trace import read_trace
for v in read_trace('.echolab/traces/20261003T031424Z-28df54.jsonl', 'verdict'):
    print(v['draft'], v['ok'], v['problems'])
"
# 実際の出力：
1 False ['数値「936」の出典がありません。ツールの結果は [[出典ID]] で引用し、差や比は比較ツールで計算してください（質問にある数値の引用は可）。']
2 True []

（台本モードで質問すると .echolab/traces/ にトレースファイルが 1 つ作られますが、それ以外にリポジトリは変更されません。）

トレースの読み方

イベントの種類

event書かれるタイミング注目するフィールド
question開始時に 1 件question 質問の原文、domain ドメインパック、llm（ScriptedLLM は台本、AnthropicLLM は本物の Claude）、model、tools 今回使えるツール
llm_callClaude を呼ぶたびに、その後stop_reason（tool_use＝ツールを呼びたい、end_turn＝下書きを提出）、usage トークン数、usd 費用、text 下書き、tool_uses
tool_call各ツール呼び出しの前name（damage_expected など）、input
tool_result各ツール呼び出しの後outcome.call_id（c1…）、outcome.sources（出典 ID と数値、unverified_inputs 未確認のデータ）、outcome.error（ゲートウェイが拒否した場合や入力エラーの説明）
verdict各下書きの検査の後draft 何番目の下書きか、ok 合格かどうか、problems 差し戻しの理由、cited 引用した出典 ID、template 下書きの原文
answer終了時に 1 件status、answer 最終的な文面、cited、cost_usd、drafts / drafts_rejected、llm_calls / tool_calls
budget_exceededコストの上限に達し、Claude を呼ばずに止まったときreason
llm_errorClaude の呼び出しに失敗したとき（API キーが未設定の場合など）kind 失敗の分類（credentials 認証情報がない、auth 認証の失敗、transient レート制限・過負荷・ネットワーク、other その他）、error SDK の元のメッセージ

トレースを読むコツ
  • まず最終行の answer を見ます。状態、費用、差し戻しの回数がひと目で分かります。
  • 回答のある数値が気になるときは、answer.cited で出典 ID（c4.change など）を見つけ、tool_result で同じ名前の source_id を探すと、元の値と計算したツールが分かります。
  • 差し戻しがあったときは、verdict の problems を見れば、どの数値に出典がなかったかが分かります。
  • 数値は文字列で保存されているため（"6192.000000" など）、丸められることはありません。

数値の忠実度の評価：試験問題で「出所の分からない数値」を調べる

評価は、evals/faithfulness/cases.yaml の試験問題を順に EchoLab に渡し、結果を確かめます。現在の問題は 8 問です：

問題 ID何を確かめるか期待する結果
damage-basic期待ダメージと各明細の引用answered、差し戻しなし
echo-score声骸スコアの引用（数値とパーセント）answered
gacha-unverified未確認のデータに基づく数値に注記が自動で付くことanswered、注記あり
compare-builds並列の計算 + 比較ツール（差・増加率）answered、c1–c4 を引用
tool-error-recoveryツールの入力エラーを読み取って呼び直すことanswered、c2 を引用
bad-draft-raw-number数値を直接書いた下書きが差し戻され、引用に直されることanswered、差し戻し 1 回
bad-draft-derived-and-unknown-id自分で計算した差や、存在しない出典 ID がどちらも差し戻されることanswered、差し戻し 2 回
never-corrected何度差し戻しても直らないとき、数値を含まない定型の回答に切り替わることfallback、差し戻し 3 回

評価を実行する（台本モード）

台本モードでは API キーも Java も不要で（試験用の計算サービスを使います）、数秒で終わります。ここでは、リポジトリ内のファイルを変更しないように、レポートと生データを一時ディレクトリ（例：/tmp/ug3/）に書き出しています：

（端末に出るレポートは Markdown の表です。ここでは紙面の都合で「内容」の列を省略しています。すべての問題に合格し、忠実度が 1.0 のとき終了コードは 0、それ以外は 1 です。）

1 問だけ実行する

--case never-corrected（--case は複数指定できます）。実測：fallback、下書き 3、差し戻し 3、合格。ID を間違えると 1 問も実行せず、使える ID を一覧表示して終了コード 2 で終わります。

レポートの書き出し先

--out パス で Markdown のレポートを書き出します（指定しなければ表示のみ）。生データ faithfulness-<llm>-<時刻>.jsonl と各問題のトレースは --raw-dir に書き出され、既定は evals/reports/raw/ です（コミットしません）。

別の問題セットを使う

--cases ファイル.yaml。形式は evals/faithfulness/cases.yaml と同じです。

レポートの指標の意味

指標（レポートの表記）意味今回の値
忠実度ユーザーに返した回答のうち、出典のない数値を 1 つも含まないものの割合。検証に合格した回答ももう一度検査し、定型の回答には数値が一切ないことを確かめます。EchoLab の設計上、この値は必ず 1.000 でなければなりません1.000
差し戻し率すべての下書きのうち、検証器に差し戻されたものの割合。これは AI が誤りをする頻度の指標で、回答が誤っている割合ではありません（差し戻された下書きはユーザーには届きません）。台本モードの問題にはわざと誤りを入れているため、ここでは高めです0.462（6 / 13）
合格したケース状態、引用、差し戻しの回数、注記などが期待どおりかどうか8 / 8
費用の合計全問題の Claude の費用の合計（米ドル）。台本モードのトークン数は台本に書いた架空の値で、費用の計算そのものを確かめるためだけに使います0.028120

問題ごとの表では、「下書き」は下書きの数、「差し戻し」は差し戻しの回数、「引用した出典」は最終回答が引用した出典 ID、「合否」は合格したかどうか（不合格なら理由）を表します。リポジトリにコミットされている基準のレポート evals/reports/scripted-baseline.md は、上の結果と完全に一致します。

台本モードと本物の Claude の違い

台本モード --llm scripted（既定）本物の Claude --llm anthropic
AI の回答問題に書かれた台本どおりで、毎回同じ質問だけを本物の Claude（claude-opus-5-5）に渡すため、毎回変わることがある
計算サービス試験用の計算サービス（Python の参照実装）。Java は不要本物の Java の計算サービス（Java 21 とビルド済みの jar が必要）
必要なものなしANTHROPIC_API_KEY などの認証情報。費用がかかります
費用の記帳一時的な台帳を使い、本物のコストの上限には影響しない本物の台帳 .echolab/costs.jsonl に記録し、日次・月次の上限（既定 1 / 10 ドル）が適用される
確かめる項目すべて：状態、忠実度、注記、引用した出典 ID、差し戻しの回数、台本を使い切ったか状態、忠実度、注記（引用や差し戻しの回数は AI によって変わるため確かめない）
実行する場所手元でも CI でも可手元で手動実行するだけで、集計したレポートだけをコミットします。CI には API キーがありません
API キーがないとどうなるか実測：--llm scripted を付けずに質問しても、EchoLab は異常終了しません。原因と対処法を説明する定型の回答「Claude API の認証情報が見つからないため、回答できませんでした。環境変数 ANTHROPIC_API_KEY を設定する（または ant auth login でログインする）か、…」を返し、状態は llm_error、終了コードは 1 です。トレースには llm_error イベントが 1 件記録されます："kind": "credentials"、「Claude API の認証情報が見つかりません（ANTHROPIC_API_KEY などを設定してください）」。--llm anthropic で評価した場合も同じで、キーのない問題は llm_error で終わり、費用は発生しません。

本物の Claude で評価するときのコマンド（キーがあり、Java の計算サービスをビルド済みの場合）：

JAVA_HOME=$HOME/.local/jdk/21 .venv/bin/python -m core.evals --llm anthropic --out evals/reports/<名前>.md

問題は 1 問ずつ順に実行します（費用が膨らまないよう、並列にはしません）。レポートの LLM の行にはモデル名が記載されます。
